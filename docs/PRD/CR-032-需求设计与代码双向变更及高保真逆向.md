## 1. 用户目标与现有缺口

目标是双向增量闭环，不是分别生成几份大体合理的资料：

`人工文档／模型变更 → 实际差异和影响 → 确认需求设计 → 独立编码授权 → 代码变更与验证 → 源码逆向对账 → 局部文档提案 → 确认新基线`

现有STORY-017/018的手工差异、白名单、配套文档／冲突控制和STORY-019的逆向草稿仍复用，但未覆盖全入口到代码、源码增量回填和删文档后的高保真实验。已有正文读写与需求索引不是逆向引擎；事实与拟议方案见[LLD](../LLD/LLD-CR032-双向变更与高保真逆向.md)。

## 2. 双向范围与权威分工

| 变更来源 | 应支持的结果 | 不允许默认发生 |
| --- | --- | --- |
| Epic／Feature／Story | 实际变动分解到必要PRD／AC／设计、实现定位与代码任务 | 改标题重写系统、父项删除级联删除代码 |
| PRD | 范围／流程／权限／规则映射到Story与设计，再形成实现差异 | PRD与AC冲突时静默择一 |
| 技术方案 | 契约／模块／实现方式变化映射到代码与适用测试 | 纯重构必然改业务需求 |
| 数据库设计文档／模型 | 字段／结构／含义／约束映射到实体、接口、迁移计划和测试 | 保存设计即执行SQL或生产迁移 |
| 产品源码 | 从真实行为／契约／权限／状态／结构生成需求设计事实和局部回填提案 | 错误实现或未授权功能自动成为已确认需求 |

- 正向工作中需求／PRD／LLD完整正文仍以文件为权威；结构化模型继承[CR-027](CR-027-Code项目设计资料与按需加载.md)的单一版本记录权威，导出MD修改先受控导入，不产生两份可编辑设计。
- 继承[CR-028](CR-028-文件与数据库按职责存储.md)：索引和摘要不是原件。但**删除资料后的本次逆向不准读取任何这些存储**；常规系统有索引／同步记录不意味着逆向输入获准。
- UI不新增手工编辑授权；代码变化涉及用户可见行为仍须先补有效UI设计，逆向现状不能覆盖用户已调整的有效设计。
- 不包含自动发布、生产迁移、隐藏备份／辅助语义包、向源码注释或字符串塞原始文档／追踪payload、根据代码猜测历史验收／负责人／排期。

## 3. 文档到代码的变更

1. GUI与受管范围外部编辑均能进入差异分析；检测只标dirty／待同步，无授权不调用模型或改代码。
2. 比较最近已同步源hash／模型revision与当前稿，提取稳定实体／AC／字段的before／after；区分文件缺失、删除实体、取消需求和删除实现。
3. 高层目标含糊先补待确认Story，跨层矛盾先列冲突；映射未知不报告“无影响”。净零、纯排版／标题等无语义影响不创建代码任务。
4. 提案列必要可写目标、配套资料、实现证据、测试／迁移风险；只读依赖不扩大白名单，人工稿保留。
5. 确认需求设计与授权代码执行分开；满足DoR／UI／DB前置后复用既有派发和受管执行，不新增第二派发入口。
6. 最小必要代码patch与测试验证后反向对账，才可形成新同步基线；保存文档或编译成功不等于全同步／验收。破坏性数据变更须有独立授权、兼容和恢复策略。

### 3.1 CR-041：区分两种同步完成，消除准入循环

文档内部一致性与文档—代码一致性不是同一门槛。未确认草稿、需求／设计冲突、部分文档落盘仍禁止开发；需求与配套设计已确认并完整应用后，可冻结该批的文档确认快照，在独立编码授权、UI／DB及派发前置满足时启动本批代码工作，即使新代码尚未生成。此时只叫“文档已确认、代码待对账”，不得称全同步或业务已验收。

旧共同同步基线保持不变，供本批diff／冲突保护；本批显式绑定新文档快照与旧代码manifest，不能要求二者事先相等。代码验证与反向对账全部完成后才发布新的共同 SyncBaseline。后续人工改文档使本批快照失效，仍须重检确认；不取消未同步冲突稿禁开的原规则。纯源码重建模式继续禁止读这些历史快照／基线。

## 4. 代码到文档的增量回填

1. **事实生成仅从产品源码取证**：解析AST／符号、路由／接口、事件、调用链、权限判断、状态转换、验证与错误分支、源码内真实持久化结构。不能读取测试、独立schema、迁移资料或数据库现状补事实。
2. 每条事实带源码快照、位置和结构值；动态调用、外部配置／服务、缺失依赖或无法解析时标未知／待核验。模型自评置信度不是正确性证据。
3. 区分原需求意图、当前实现事实和缺陷／未实现；业务不变重构只补必要方案与实现定位，不强迫修改Epic／Story；代码删除不自动取消需求。
4. 常规增量模式中文档仍在，可使用共同基线与人工稿做三方合并和冲突保护，但不能把这些资料当源码事实证据；**删文档重建实验没有此上下文，必须从零纯源码恢复。**
5. 回填只更新受影响实体／章节，保留ID、父关系、人工稿和历史验收；无可靠旧身份不能宣称恢复原ID。需求确认／验收状态不得由源码推造。
6. 源hash／模型revision／权限／分支变化使旧包失效；跨介质部分失败标pending并安全对账。同因果同内容防回环，后续人工新改动仍应被识别。

## 5. “只有代码”的高保真重建

### 5.1 输入边界已确认

- 允许：实际产品程序源码及其中原本用于实现的类型、校验、权限、状态、接口、查询或结构定义。源码中的真实DDL／字段声明可取证，但不能把独立schema／测试／模型文件改名搬入代码目录再算源码。
- 禁止：测试／测试夹具、独立schema或迁移资料、需求／设计／说明文档、配置／运行数据库、语义包／归档、旧索引／会话／Git历史、评价原文、恢复前注入的追踪信息。必要依赖源码不在输入时明确未知，不向外抓资料补齐。
- 原有注释只是待核对的辅助源码线索，不能替代可执行行为；正向不得为提高逆向分数藏原PRD／LLD、稳定ID映射或特殊恢复标记。
- 文件名和目录仅定位，不直接当Epic／Feature划分。生成端使用独立空会话和硬隔离目录，不能继承正向生成对话。

### 5.2 精度策略

采用`源码结构解析 → 带证据的行为／数据事实图 → 业务能力和可观察场景 → Story／候选AC → Feature／Epic → PRD／方案／DB → 交叉校验`，而不是一次自由总结整库。下层事实先确定、业务分组再归纳，跨层使用同一事实图以降低漏项和互相矛盾。

高相似度目标是原层级和业务语义接近，非原句复刻。**源码到需求是多对一映射，不保证唯一反推出原业务动机、原分组或未编码需求。**即使重建了合理层级，也必须在独立评价中验证与原层级的匹配，不能把“都看起来合理”当高度相似。缺证据项明示未知并计入原资料覆盖率，不能用缩小分母宣传高精度。

源码有缺陷时重建现状及差异候选，不把错误实现变成业务标准；源码缺数据库约束时DB资料必须列缺口，不编造线上schema。

| 维度 | 必须分开报告的口径 |
| --- | --- |
| 类别与实体完整性 | Epic／Feature／Story／AC、PRD、方案、DB类别与实体覆盖，缺失类别不得忽略 |
| 层级接近程度 | 按业务语义匹配实体后评价父子关系／分组；原ID不可得则列不可恢复，不要求猜号，但不能只验自生成树合法 |
| 业务规则与AC | 独立冻结原子事实precision／recall／F1，角色、目标、主分支、状态、权限、约束、边界和异常逐项；关键错误不可平均抵消 |
| 技术方案 | 模块职责、接口／事件、核心依赖／调用和实际存储机制逐项比对，未编码历史取舍列未知 |
| 数据设计 | 源码可证名称／类型／nullable／default／PK／FK／UNIQUE／CHECK／关系逐项精确匹配；不把缺失或依赖外部schema的事实标正确 |
| 未知与编造 | 全原资料覆盖、可恢复子集成绩、不可恢复比例并列；无证据断言不能标已确认，关键权限／规则编造不得放行 |
| 文字与收敛 | 措辞不要求相同，文字相似度辅助；同源码重复重建不重复实体，代码变化后局部对账、不回环 |

纯源码输入和语义目标已确认，**0.95等此前增强模式的建议不移植为本次承诺**。源码可证关键事实必须准确；量化语义／层级最低门槛需先无泄漏试测、再固定并由用户确认。未测试不得说已经高精度，未知也不能被当作正确。

用户举例的实验：评价端独立冻结正向原资料D0；生成系统后，恢复端仅收到源码C0，在新会话／隔离目录生成D1；D1封存后仅评价端比D0。评价基准不是逆向输入。再改代码C1重建D2，分别检查新业务／纯重构／删除与人工冲突，不为旧文相似度掩盖当前变化。详见[盲测方案](../Test/TEST-CR032-双向变更与逆向保真验证.md)。本批不删除真实文件或运行该实验。
