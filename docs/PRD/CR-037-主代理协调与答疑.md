## 1. 背景与用户目标

现有设计已覆盖派发、依赖等待、受管执行、验证与交付，但缺口在于**执行过程中的协作**：工作代理遇到具体问题只能失败或阻塞，派发者要等到结束才知道结果，评审发现问题也无法定向退回同一个受管运行。使用者仍需自己串联「谁问、谁答、谁判断结果够不够」。

使用者要的是一套稳定分工：

1. 一个协调者把目标拆成子工作并派发，掌握全局进度与验收口径。
2. 工作代理专注执行，遇到真正挡住它的问题时向上提出，而不是自行猜测或扩大范围。
3. 协调者能依据已确认资料直接答疑；超出自己权限的部分转用户决定。
4. A 封存后，runner 按冻结计划将引用直达 B，或由大管家转发引用。B 发现缺陷时，大管家发起定向退回，runner 从受检修订定位原 A 并按证据控制交付。

目标：把这条协作链路纳入受管执行，使等待、答疑、返工、验收都有可追溯记录和明确责任人，且不削弱既有权限、预算和证据门槛。

## 2. 角色与权威

| 角色 | 职责 | 明确不承担 |
| --- | --- | --- |
| 使用者 | 目标、范围、优先级、关键业务取舍、最终验收 | 逐步指导实现细节 |
| 协调者（大管家） | 拆解、派发、答疑、转发候选引用与反馈、发起定向返工 | 阅读每份产物正文、代签业务验收或改写运行事实 |
| 工作代理 | 执行子工作、提出具体问题、提交候选结果与证据 | 自行扩大范围、改 AC、提权、绕过权限或预算 |
| 受管执行引擎（runner） | 计划校验、派发准入、租约/租期、消息持久化与投递、证据与交付记录 | 替协调者判断业务取舍 |
| 验证流程 | 按冻结计划执行检查、绑定证据、失效传播 | 以 exit 0 或模型自评代替客观验证 |

权威边界不变：需求/AC 以文件为准，运行与协作记录以 SQLite 为准。协调者身份需要绑定到真实受权主体，不接受前端或模型自报身份。

## 3. 本次范围

### 3.1 协调与派发

- 协调者依据已冻结的任务计划提出子工作；子工作包包含目标、边界、必需输入修订和交付要求，自包含，不能隐含扩大授权。
- 子工作派发前经 runner 校验：依赖、能力（CLI/版本/模式）、最低难度、模型/effort 允许集、权限范围、根预算余额、写入范围冲突。
- 同一 Story 内的子调用沿用根 Attempt，获得独立调用身份和受管工作范围；不因增加子调用而提高 Task fence 或改变根指针。
- 协调者不能把无法完成或越界的工作静默降级给其他执行器；不合格组合拒绝并报告具体原因。

### 3.2 答疑与决策

- 工作代理只就影响当前工作的具体问题提出询问，附上问题、来源、受影响分支和已尝试的信息。
- 阻塞性问题使该分支进入等待，其他独立分支继续；不因一个提问暂停整个批次。
- 协调者可以依据已确认需求、设计、代码事实直接回答技术问题，答复须注明依据来源与修订。
- 下列事项必须转用户决定，协调者不得自行裁决：需求范围、验收标准、权限扩大、成本承诺、不可逆操作、外部系统写入。
- 用户决定若改变冻结基线、授权或验收标准，受影响工作须重新确认计划后才能执行；未变化的部分继续。
- 消息收讫不等于问题已解决；只有明确答复并登记有效处理才算关闭。

### 3.3 审查、返工与验收

- A 提交方案、报告或代码后，runner 封存不可变候选修订并登记来源。冻结计划已指定接收者时，runner 直投该修订的引用给 B。需要协调者选派时，由大管家转发引用和结构化工作目标。两条路径均由 runner 校验接收者、权限和精确修订，并记录实际消费。大管家默认只接收引用和必要元数据。
- B 发现问题时，提交受检修订、受影响 AC、问题位置和证据。大管家请求定向退回，runner 从受检修订查出原产出调用和原执行者。原生引用可用且兼容时，在 A 的原 CLI 会话中返工。
- 返工受预算、轮次、权限和写入范围约束，旧写进程确认停止后才启动替代调用。新提交生成新修订，受影响的消费与证据按需重验，独立分支继续。重复或过期反馈不得启动新返工。验证器或环境故障进入验证故障处理。
- runner 根据冻结 AC、验证计划、当前候选修订和输入基线判定能否技术交付。候选声明、回执、审查意见和退出码均不能单独放行。业务验收由使用者或事前授权的客观规则负责。

### 3.4 可靠性与恢复

- 问题、答复、回执、返工、决策与完成通知持久化，支持补读、去重和幂等处理。
- 协调会话重连或恢复后，能续接未关闭的问题；续行前复核身份、当前授权、预算、工作区和计划。
- 适配器须确认回到同一原生线程才登记续接成功。引用缺失、过期、撤销或不兼容时，按权限和计划显示新上下文或阻塞，重放聊天仅用于重建上下文。
- AI 侧栏普通会话切换视图、从历史重开或应用重启后，可继续原生线程。发送前重验权限并保护草稿。切换 CLI 依旧另建会话。侧栏已有受管运行可定位原任务并处理返工，普通聊天仍使用自己的会话身份。
- 协调者离线、决策超期或预算不足时，等待原因和责任人对使用者可见；期限内可恢复，届满进入明确阻塞。
- 补投消息不会让已完成的工作重跑。

## 4. 不做事项

- 本批授权为需求、交互设计稿及设计验证。正式软件、运行配置、依赖与构建另走授权。
- 不接入真实 CLI、不创建真实任务、不运行 runner、不迁移数据库。
- 不新增第二套任务/运行权威，不为协作另建可编辑需求入口。
- 不引入「协调者自动批准自己提出的权限或成本变更」这类自证通道。
- 不把工作代理数量、并发上限或模型品牌当作能力证明。

## 6. 决定、风险与待确认

已确认：

- 2026-11-19：用户确认「主代理派发、答疑、审查」的协作方向；本批按需求/设计调整执行。

代理按既有规则确定的默认口径（非用户逐条确认）：

- 大管家以结果引用和反馈为路由输入，技术证据归验证流程，业务验收仍归使用者或事前授权客观规则。
- 提问只处理影响当前工作的具体问题，不代替需求收集；不因提问扩充范围。
- 协作消息与运行记录同库，不新建独立消息数据库。
- 未获编码授权前，协作能力保持设计状态。

风险与待细化：

- 原生会话续接在不同 CLI 上能力不一，需按适配器实测；不支持的组合按权限和策略显式降级或阻塞。
- 协调者本身也是模型调用，其答疑可能出错；因此答复须标注依据来源，涉及验收/权限的问题一律转用户。
- 决策等待时长与协调者离线判定阈值需在实施前确定；到期必须明确阻塞已由 AC-STORY-046-12 确定，不再作为可选行为。缺少有限阈值不得启动需要该关口的真实计划，不影响无此依赖的独立范围。
- 侧栏续接与返工界面版本、覆盖及剩余协作界面缺口见 [UI-CR037](../UI/文档/UI-CR037-协作场景覆盖.md)。

用户在本轮明确了大管家传递结果、B 发现问题后转原 A 返工，并要求 AI 侧栏会话可以接续。继续使用原受管流程，补充普通侧栏原生续接验收。
