# CR-047：单特性执行与需求设计防遗漏

- 类型：既有研发执行／验收能力细化；日期：2026-11-20。
- 来源：用户要求研究「史诗/特性/用户故事、设计、方案写了，AI仍漏项与设计不符」的原因，查GitHub及论文，并重申「一个会话最多只能执行一个特性的需求」。本次授权调研、研发规则及需求／方案调整，**不授权本增量正式编码、依赖安装、运行配置或发布**。
- 状态：该单特性原则按直接指令确认；平台方案设计中，未实现、未验收。研究不能承诺生成式模型从此零错误；保证目标是可检测的越界与漏证不得被静默放行。
- 归属：复用EPIC-002与FEAT-018／019／020。STORY-054承接必需源和约束工作包；新增[STORY-068](../Plan/Story/STORY-068-单特性执行会话与范围门禁.md)承接单Feature执行身份；STORY-059承接检查点恢复；STORY-055承接覆盖证据门禁。不新建完整任务平台或重复业务Feature。
- 依据：[根因与外部研究记录](../Test/REPORT-CR047-防遗漏根因与研究.md)、[机制方案](../LLD/LLD-CR047-单特性工作包与覆盖门禁.md)。

## 1. 已确认问题

已有文档的稳定编号、设计先行及DoD不等于代理实际遵循，亦不等于正式执行层已经实现。上一轮主会话同时实施7个Feature；旧设计入口迁移未完整继承预览／导图；模型／工具输出与接口委派有代际和命名错配；构建／少量GUI不能覆盖所有AC和视觉状态。主代理未把已有规则转为逐项执行的台账及阻断，对此负执行责任。长上下文退化是已发表研究揭示的一般风险，但没有本会话压缩前后逐条载荷，不把「被压缩删掉了」当确定原因。

## 2. 本次范围与规则

### 2.1 一个执行会话，一个Feature

- 平台已经把“按特性派发”作为派发范围入口；本条把该原则落实到会话身份，而不只停留在选择范围。执行会话绑定一个稳定 `projectId + featureId`，可顺序执行该Feature内一个或多个Story；不是同时把全部Story正文／全库塞入上下文。
- 创建执行会话时服务端校验：Feature属于该项目、Feature源可读、唯一父链可解析；绑定后`featureId`不可在会话更新中改为另一Feature。普通聊天会话不绑定Feature，也不显示为执行会话。
- 同一Feature可以有多个会话（分任务或恢复），但每个会话只属于一个Feature。派发批次仍可含多Feature，UI按Feature分组说明将创建多个独立执行会话，不共享会话身份。
- 发送、恢复、历史、任务交接均以持久Feature身份为准；Feature源变更或缺失时标待核验并阻止把该会话当新目标，不从会话摘要重建归属。
- 协调会话可跨Feature只读分析、排依赖和收集报告，不直接编码、不借子代理继承跨Feature写权限。每个Feature独立执行会话／工作包；同Feature子工作范围只能缩小并继承其身份。
- 用户一次跨Feature请求先拆为协调批次；每个Feature的执行、结果和验收独立。不能把「整个系统」「这次CR」「共享组件」当人工拼出的Feature规避粒度；跨Feature共享变更须明确业务归属、受影响接口及独立责任包。
- 当前执行遇另一Feature的写入需求，登记依赖并移交；新会话不是自动授权，须核对原批次是否已明确授权该Feature。角色切换要新受检会话，不能沿原超长编码线程换标识继续。
- 集成只针对已交付候选、限定产物与事前定义的测试，不得变成跨Feature开发。发现修复须回对应Feature工作包或明确的集成缺陷工作包，保原业务归属，不静默扩权。

### 2.2 文档不靠摘要成为权威

- 形成完整源清单和版本：Feature目标与不包含、Story/AC全集、相关PRD、适用UI页面／状态／视口／主题、LLD接口／约束、适用DB、授权和目录规则。历史与现行显式区分。
- 必需约束有稳定ID与原文锚点，不仅保「有设计」链接；加载时核对缺源、重复ID、来源矛盾、入口迁移继承、无法验证的视觉／工具能力。未读／不支持／不完整不能默认为已满足。
- 上下文分两层：紧凑常驻执行卡（单Feature、当前Story、禁止项、必需AC/约束、版本、下一步）；正文／代码／日志按需读原源。关键约束不能被检索排名丢掉，源文件正文仍是事实来源。
- 代理回述身份和待做义务只是对齐诊断，不是强门禁或正确性证明；运行侧必须独立核查范围和证据。

### 2.3 上下文恢复不只是一段会话总结

- 在模型上下文外保存受检检查点：Feature／Story／AC、工作层级、工作包版本、代码HEAD与未提交diff指纹、已做／未做、失败与未验证、实际证据、调用代次及未知副作用。摘要不得凭空恢复权限或完成状态。
- 压缩、fresh、断线、模型失败或主动续接后，先重新读取工作包与当前源版本并对账，确认旧writer状态再继续；有变更／缺源则暂停重新预检。必需信息无法放入预算时拆小Story步骤或续新受检会话，不静默截断。
- 上下文预算按真实token及经验证的有效能力管理，未知显示未知；不按模型名称猜上限，不把论文32K结论当所有当前模型的固定阈值。

### 2.4 漏项不能被一句「完成」覆盖

- 全集义务台账：每个AC／UI状态／LLD强约束分别映射任务、实现位置、验证方法、证据与结果。状态区分待做、失败、未执行、通过、不适用（有依据）；不适用和取消不能由代理临时决定来凑100%。
- 进入下一阶段须满足该阶段完整门槛。`exit 0`、Todo全勾、三票多数和模型报告不能替代视觉／功能／权限证据；视觉验证器不可用必须阻塞相关验收，不降低设计。
- 证据绑定采用设计与实现版本、相同数据／视口／主题／状态；源或代码变化时只使受影响证据失效，保历史。完成消息只从有效台账生成，不由自由文本改变Story状态。

## 3. 本次不包含

不实现持久runner／新记忆平台／模型微调／视觉引擎，不自动开启跨Feature会话，不更改真实CLI权限或安全模式，不读取私密会话／生产数据。平台屏幕与数据结构目前仅明确所需覆盖和契约，**没有本次可视设计锁版，不准进入UI编码**。不删除历史验收，不把当前软件已有字段当未来门禁已实现。

## 4. 验收与实施顺序

具体AC以STORY-054/055/059/068增量为准。推荐先单Feature绑定与必需工作包，再恢复对账，最后覆盖／视觉／完成门禁；每个Feature独立执行会话，按既有授权流程另行正式开发。先制定注入漏项／换源／上下文压缩等隔离评测，证明能发现并阻断，再讨论模型遗漏率改善，不能以一次成功宣布永久保证。
