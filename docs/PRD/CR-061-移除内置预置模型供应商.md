# CR-061：移除内置预置模型供应商

- 状态：**已实现并通过自动化验证（2026-11-22：cargo test 通过、npm run build 通过、冒烟供应商链路改为自建并通过）**。
- 来源：用户 2026-11-22 指令：「内置供应商移除，其他的先不要动」。
- 关联：[FEAT-014 供应商模型与能力适配](../Plan/Feature/FEAT-014-供应商模型与能力适配.md)（唯一父项）、[STORY-081](../Plan/Story/STORY-081-移除内置预置模型供应商.md)、[LLD-CR061](../LLD/LLD-CR061-移除内置预置模型供应商实现.md)；复用 [DB-FEAT-001 既有存储设计](../DB/DB-FEAT-001-知识授权与工作台数据设计.md)（无新增表）。

## 1. 背景与目标

软件在首次创建本地库时会写入一个预置模型供应商「TierFlow（预置，需填密钥）」（`prov-tierflow-default`，anthropic 协议，两个端点 `https://tierflow.cn`，两个模型 `tierflow` / `tierflow_pro`）。它不带密钥，实际不可用，但对用户是干扰：设置页凭空出现一个自己没配过的供应商，且暗示「必须用它」。

用户要求移除内置供应商。

目标：新装用户不再看到任何预置供应商；老装用户库中遗留的预置行被清理；**用户自己创建的同名/同协议供应商完全不受影响**；冒烟与真实验证链路不因移除而失效。

## 2. 本次范围／不做事项

**包含**

1. 删除后端预置逻辑：`db.rs` 的 `seed_default_provider` 及其调用点（`migrate` 末尾的 seed 调用）。
2. **不自动清理老装用户的遗留预置行**（用户 2026-11-22 追加指令：「老用户不用管，用户自己会删除的」）：老装库里已存在的预置供应商由用户自行在设置中点击删除。设置页本就有删除入口，后端 `provider_delete` 会连带清理该供应商独占的密钥条目，用户无需额外操作。
3. 冒烟链路改造：`smoke_set_tierflow_key` 不再把密钥挂到预置供应商，改为在冒烟库中自建一个专用供应商（anthropic 协议 + 对应端点 + 密钥 + 至少一个模型），使真实网关对话验证（`chat_send` 经 claude + tierflow、真实工具调用等）继续可用。
4. 前端冒烟套件同步：不再断言「应有预置 TierFlow 供应商」，改为断言「冒烟供应商由套件自建且可用」。

**不做事项**

1. **不删除用户自己配置的供应商**——即使名字也叫 TierFlow、协议相同、端点相同。
2. 不改动模型供应商的配置界面、协议字段、模型发现、密钥存储与指纹检测等任何既有行为。
3. 不改动内置 CLI SDK 登记（claude / codex / grok）——那是 CLI 能力，不是模型供应商。
4. 不改动内置示例项目与示例知识库（用户明确「其他的先不要动」）。
5. 不新增供应商模板/预设机制（不把「移除预置」变成「换一批预置」）。
6. 不迁移或改写用户数据；清理动作只针对固定预置 id，且不触碰用户密钥文件（`secrets.json` 中与预置供应商相关的条目按 id 精确清除）。

## 3. 业务流程

### 3.1 新装

1. 用户首次启动 → 建库 → **不再写入任何供应商**。
2. 设置 → 模型管理显示既有空态「尚无供应商，请新建。」→ 用户自建供应商、填密钥、拉取模型。

### 3.2 老装升级

1. 启动**不做任何预置相关的自动清理**——老装库里遗留的预置供应商原样保留。
2. 用户在设置 → 模型管理中看到该供应商，自行点击删除；删除时后端连带清理其独占密钥条目（既有 `provider_delete` 行为）。
3. 用户自建的供应商全程不受影响。

### 3.3 冒烟（真实网关验证）

1. 冒烟套件在冒烟库中自建供应商（固定 id 与预置不同，命名为「冒烟 · TierFlow」），写入端点、模型与测试密钥。
2. 真实对话、真实工具调用等用例改为引用该自建供应商 id，行为与此前一致。

## 4. 规则与边界

- 本次不涉及任何自动清理逻辑，因此不存在误删风险；预置供应商的移除完全由用户通过界面删除触发。
- 用户手动删除时，既有 `provider_delete` 只清理该供应商**独占**的 secretRef（被其他密钥复用的保留），用户自己的供应商与密钥不受影响。
