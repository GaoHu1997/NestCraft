## 2. 现行存储分工

| 数据类别 | 权威介质 | 数据库职责 |
| --- | --- | --- |
| 完整 PRD、愿景／Epic／Feature／Story、AC 与需求确认记录 | 项目 Markdown 文件：`docs/PRD/`、`docs/Plan/` | 标题、归属、源定位、hash、版本、状态等派生索引；禁止第二份可编辑正文 |
| UI 原型、HTML/CSS/JS、图片及其它设计资源 | 项目 `docs/UI/` 文件与资源目录；保留唯一公开入口 | 资源清单、版本、关联 Story/AC 及受检引用；不能把整个资源包改存 TEXT／BLOB／Base64 |
| 完整方案、ADR、说明文档 | 项目 `docs/LLD/` 等既有目录中的文件 | 摘要、关联、源定位及派生查询，不替代方案正文 |
| 知识库上传原件、会话附件、办公源资料和产物 | 分库／分项目的受管文件目录，原格式与完整字节保留 | 稳定文件 ID、名称、格式、大小、hash、存储引用、所属范围、导入／解析状态和关联 |
| 解析文本、切片、预览与检索数据 | 原件的派生产物；大文本／预览文件单独存放 | 可存必要的全文索引、检索片段、切片定位与解析版本；可重建、不冒充原件或第二份文档权威 |
| 项目记录、知识授权、配置引用、会话消息、执行状态／审计及查询关系 | SQLite 等适合结构化事务的数据库 | 业务权威，不因要求文件存储而全部搬成 JSON 文件 |
| 数据库设计的结构化模型 | 延续当前设计资料需求允许的版本化数据库模型记录 | 表／字段／类型／约束可存数据库，与 AI 供应商 `model` 区分；完整说明、图稿、导出仍是文件，不维持两个可编辑模型源 |
| 长日志、完整交付报告、不可变文档快照、证据图片 | 受管文件目录 | 运行状态、结果摘要、清单、版本/hash 与文件引用；不把完整正文藏入任意 JSON 字段 |

数据库可以有合理 TEXT／JSON 字段，如会话消息、结构化模型或策略；本变更否定的是无差别塞入完整文档／原件，不是按字段类型禁止数据库。

## 3. 原件、权限与一致性约束

1. 上传／导入模式：持久保管原始文件成功后才可报告导入成功；解析失败与保存失败分开，解析失败不得删除原件。仅复制字节成功不等于已经耐久保存，正式方案必须验证崩溃与磁盘错误。
2. 目录绑定模式：原件仍由外部目录所有者管理，明确不等于托管备份。重扫、移除库绑定、撤权、清空索引不能修改或删除外部原件。
3. 原件使用稳定文件 ID 与修订，文件名不是 ID；同名不覆盖、移动不自动换身份。解析产物绑定原件 hash 和解析器版本；原件变化使旧解析／索引失效，不能混用不同修订。
4. 文件是正文权威。保存先检查目录、身份、权限与基线 hash，再保存可恢复版本并原子替换。文件成功、索引失败应记录待同步并重建，不能从数据库旧投影回写旧正文。
5. 文件操作与数据库事务不假称跨介质原子提交；采用可恢复登记与对账，崩溃后区分原件已保存、登记待完成、解析待重试。缺失／损坏对象不允许作为有效引用或验收证据。
6. 原件、解析结果、索引、预览及 AI 读取均受同一库／项目权限约束。CLI 不因文件存储取得全盘路径权限，撤权立即阻止后续读取和缓存复用。
7. 搜索／需求索引可重建；授权、原件登记关系、会话、执行和验收历史不可从索引猜测恢复。物理删除须独立授权与引用核查，本次不定义自动清理或不可逆删除。
8. 项目文档可按已有版本管理约定纳入 Git；真实上传原件、个人知识、会话、数据库和受管运行资料不自动入 Git，不自动上传云端。
