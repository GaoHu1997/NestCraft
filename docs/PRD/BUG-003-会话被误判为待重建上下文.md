## 1. 现象

会话发送过一轮后，输入区上方出现阻塞横幅：

> 上下文待确认重建
> 原因：引用缺失（历史无原生绑定）。历史记录仍可查看；未发送草稿已保留。

同时输入被锁定（`composerLocked`），必须点「确认重建…」才能继续发送，且该操作会清空原生引用并写入一张上下文断点卡。

## 2. 触发判定的代码事实

- 后端派生视图：`src-tauri/src/commands/chat_binding.rs:565-601` 的 `derive_view`。
  - 有 `nativeThreadRef` → `native`；
  - 用户显式确认过（`fresh-…`）→ `fresh`；
  - **`message_count > 0` 且无引用 → `freshPending` + `REF_MISSING`（`chat_binding.rs:596-600`）**；
  - 不支持续接的 CLI → `UNSUPPORTED_CLI`。
- 调用点：`src-tauri/src/commands/chat.rs:126-135`，`derive_view` 只接收 `session_role / cli_id / thread_ref / 消息数` 等，**没有接收 `runner`**。
- 前端拦截：`src/modules/chat/ChatPanel.tsx:288-292` 由 `binding` 求 `composerLocked`；`ChatPanel.tsx:973-985` 发送前遇到 `freshPending` 直接拒绝并弹确认；`ChatPanel.tsx:1221-1229` 渲染横幅。
- 文案来源：`ChatPanel.tsx:81` 与 `chat_binding.rs:56` 的 `REF_MISSING` 映射。

## 3. 两个可复现的真实场景

### 3.1 平台通道会话（必然复现，主因）

`runner=platform` 由 `platform_agent::send_platform` 作答（`platform_agent.rs:679-727`），上下文来自 `platform_context_runtime`（历史消息 + 摘要块），**设计上不使用 CLI 原生线程，也从不写 `nativeThreadRef`，不写 `execution_session_turn`**。但 `derive_view` 只用「普通会话 + 有消息 + 无引用」判断，于是平台会话在首轮结束后**立刻**变成 `freshPending`，第二轮发送被前端拦下。

本机库只读核对（`%APPDATA%/com.agentworkbench.app/workbench.db`）：

| 会话（前 8 位） | runner | 消息总数 | 角色分布 | nativeThreadRef | 最后轮次 | 更新时间 |
| --- | --- | --- | --- | --- | --- | --- |
| `sess-b496…` | platform | 10 | user 1 / assistant 1 / tool_use 4 / tool_result 4 | NULL | 无 | 2026-11-24 14:13:47 |

即：该平台会话**只发送过一轮**（1 条 user、1 条 assistant、4 组工具调用），没有重建断点卡，`nativeConfirmedTurnId` 为空——首轮完成后就进入了待确认状态，与用户描述完全一致。这是确定性缺陷，不是偶发。

### 3.2 CLI 会话首轮未结算（有条件复现）

CLI 路径正常时应由 `settle_turn` 写入 `confirmed` 并把 `nativeThreadRef` 落库。本机库中既有正常样本（`sess-e206…` 19 条消息、`has_ref=1`、`outcome=confirmed`），也有首轮未结算样本：

| 会话（前 8 位） | runner | 消息数 | 角色分布 | turn 记录 | nativeThreadRef |
| --- | --- | --- | --- | --- | --- |
| `sess-f73a…` | cli/codex | 1 | user 1 | 空 | NULL |
| `sess-1c23…` | cli/codex | 1 | user 1 | 空 | NULL |

用户消息已落库，但既无 assistant 消息、也无任何 `execution_session_turn` 行，说明首轮在结算前中断（应用关闭 / 窗口销毁 / 进程异常 / 流终止早于结算）。此时第二轮同样命中 `REF_MISSING`。

按 CR-068 J11，**这条提示本身是刻意设计**：不允许在引用丢失时静默新建上下文。问题在于它无法区分「平台会话不适用」与「CLI 首轮没跑完」，用户无法判断该不该点重建。

## 4. 影响

1. 平台会话每新建一次，第二轮就要多点一次「确认重建」，并永久留下断点卡；多轮体验被切断。
2. 用户被引导去「重建上下文」，真正原因却是通道不适用，容易误判为软件故障或历史丢失。
3. 首轮中断的 CLI 会话没有说明「首轮未完成」，同样给出误导性原因。
4. 未发送草稿、历史查看均正常——这一点与提示文案所述一致，不属于数据丢失。

## 5. 修复目标与验收标准

- **AC-BUG003-01**：给定 `runner=platform` 且已有消息、无 CLI 原生引用的会话，则不派生任何 CLI 绑定状态，不显示「上下文待确认重建」横幅，输入不锁定，可直接发送第二轮；发送仍走 `send_platform`，历史由平台上下文回放。
- **AC-BUG003-02**：给定 `runner=cli`、已有消息且无引用的会话，仍保持 `freshPending`／`REF_MISSING`，不得因为本次修复放行静默 fresh（CR-068 J11 不回归）。
- **AC-BUG003-03**：给定 CLI 首轮未结算（有 user 消息、无 turn、无引用）的会话，横幅原因需能表达「首轮未完成、尚无原生线程引用」，并给出与原 `REF_MISSING` 等价的出路（确认重建或另建会话）。
- **AC-BUG003-04**：正常 CLI 续接（`native` / 已确认 `fresh`）行为、CAS 结算、兼容键与撤权阻塞均不变；`derive_view` 的既有单测保持通过。
- **AC-BUG003-05**：平台会话切换回 CLI 仍被禁止（已有消息），不产生「平台历史交给 CLI 续接」的混合状态。

## 6. 不包含

- 不恢复或改写任何已发生的会话历史；不做数据迁移。
- 不改变 CLI 原生续接协议、兼容键、授权快照与 CAS 语义。
- 不新增「平台会话也写原生引用」的假绑定。
- 不改动平台上下文预算、摘要与工具循环。

## 7. 用户当前的恢复办法（不改代码即可）

1. 若该会话是「大管家」平台会话（会话配置里运行通道为 platform）：这是缺陷，可先点横幅中的「确认重建…」继续本轮对话；后续新会话仍会再次出现，需等修复。
2. 若是 CLI 会话且首轮没有正常回复（被打断/关闭窗口）：点「确认重建…」会在新上下文继续，历史保留；若希望保留原线程，请先确认 CLI 进程已正常结束再发下一轮。
3. 都不影响历史查看与草稿。
