## 3. 调研结论（技术参照，不引用参考目录）

1. **思考等级知识库**（B2）：用户指定的 MIT 开源项目维护了 87 条模型家族条目（OpenAI/Anthropic/Qwen/Kimi/Grok/GLM/DeepSeek/Step/Mistral/Gemini/MiniMax/MiMo/混元等及生图专条），字段含匹配 patterns、档位→wire 拼写映射（off/minimal/low/medium/high/xhigh/max，null=该档不发参数）、defaultEffort、contextWindow、maxTokens、模态与协议 compat。匹配算法为宽松归一化子串＋词边界＋最长命中优先；未命中返回 undefined。其供应商探测读取 `/models` 列表中的推理信号字段（supported_features/supported_parameters 含 reasoning、supports_reasoning 等布尔旗标、capabilities.effort/thinking.supported），三态输出（true/false/unknown，沉默不等于拒绝）。本项目按 MIT 保留版权与许可声明后引入知识库数据与匹配逻辑，落地为本地内置知识库文件；「先从供应商获取」指读取已保存端点的模型列表推理信号，不新增用户填写。
2. **CLI/SDK 快速加载**（D5/E4）：用户指定的 MIT 参考项目有两套可借鉴机制——①内存快照：启动后台探测＋定时保温，UI 只读廉价快照，毫秒级返回；②模块级缓存（TTL 10 分钟）＋首帧渲染旧值（stale-while-revalidate）＋逐工具并发渐进刷新，单工具失败不拖累其他；版本检测优先纯文件系统（PATH 并发 stat＋realpath 向上找 package.json 读 version，校验 bin 归属），`--version` 仅作超时兜底；latest/版本列表用 HTTP 直连 npm registry 拿 dist-tags/versions，不 spawn npm；安装状态与版本号解耦（先报「已安装（版本未知）」再异步补版本）。本项目现状为打开设置时对 3 个 CLI 串行执行 `npm ls -g`＋`--version` 兜底（sdk.rs detect_one），是慢的根因。
3. **F6 根因调查**（代码事实，2026-11-22 读取）：
   - 内置工具注册表（capabilities.rs BUILTIN_TOOLS 原有 6 项：fs.read、knowledge.*、ssh-exec）只是 DB 启停开关；chat.rs/dispatch.rs 派发链路**没有任何代码把这些工具或其开关传给 CLI**，CLI 原生工具集不受其影响——「AI 识别不到」属实：它们从未到达 AI。
   - MCP 工具：claude 派发时 stdio 服务器会写入 `--allowedTools mcp__<name>`，HTTP 服务器只写 mcp-config 不进 allowedTools；codex 走 config overrides。MCP 工具能否被 AI 看到取决于 CLI 自身连接，与 Tools 页开关无关。
   - **并行进展（CR-060，另一执行会话，2026-11-22 同日）**：工作区已出现内置 `workbench` MCP 服务器（ai_tools.rs，12 个 workbench_* 工具），派发时自动注入 claude/codex，且 tools/list 与 tools/call 读取 capability 表启停——这 12 个新工具的开关**真实生效**。注意：该并行工作的源码注释误标为「CR-059」，其文档归属实为 CR-060/STORY-079/FEAT-023；编号冲突需由集成负责人统一修正源码注释，本 CR 不修改其源码。
   - 结论：Tools 页按「来源」重组（F7）时区分两类内置工具——原有 6 项仍「注册表开关 · 尚未注入会话」（BUG-CR059-01 未修复）；workbench 12 项经 CR-060 已真实注入。修复方向（把原有 6 项也接入注入契约，或明示未接入）在 LLD 阶段确定并经用户确认取舍。

- **r8/G11 协议→端点强绑定**：密钥选定 Chat/Responses 后请求与探测一律走 OpenAI 端点，选定 Anthropic 走 Anthropic 端点；只有选「默认」才沿用供应商默认协议。行内按钮显示「协议 · 端点」（如 `Responses · OpenAI`），浮层选项带端点标注。
- **r8/G12 按密钥探测模型范围**（参考 MIT 开源实现）：保存后异步探测每个启用密钥的 `/models`，在「本供应商已声明模型」集合内写范围——①全部支持 → 不写范围（空＝全部，后续新增自动覆盖）；②部分支持 → 写入交集并标「自动」；③手动已配置 → 只追加本次新增且被支持的模型，标「手动」；④激活密钥 <2 时不探测（单密钥即全支持）。探测走该密钥自身协议对应的端点；失败不写空范围（保留上次结果）。范围表单另提供「立即探测」「清空＝全部」，并显示「已选 N / 总数」。
- 密钥「模型」范围编辑改为**小按钮卡片**：每个已配置模型一枚 mini 卡片（仅显示名，title 带 ID），点击切换；**选中态只用高亮（边框＋浅底＋字色），不放对勾、角标或任何其他标识**（r3/G5）。全不选＝全部模型。
- 密钥行内表单的**取消/保存右置且取消在前**（r3/G5）。
- 供应商默认协议**改为一行均分选择卡片**（r3/G8）：Chat / Responses / Anthropic 三个等宽卡片，选中高亮，无对勾、非下拉。
- 切换协议时下方端点协议联动：Chat/Responses → OpenAI 端点；Anthropic → Anthropic 端点。地址保留；两个端点始终并列可填（r3/G7「更多端点」只是把第二个端点输入框展开/收起）。

### 4.2.1 生图配置（r3/G4）

入口：模型管理页大标题同行最右侧**生图图标按钮**（与本页标题同一行、右对齐）；点击打开「生图配置」弹层。

- **总开关**：开启时向 AI 提供 `generate_image` 工具（随内置 workbench MCP 注入）；关闭即注销工具、所有入口拒绝生成。状态文案「已开启 · tool 已注册／已关闭 · tool 注销」。
- **多生图模型有序列表**（本项目差异点）：候选＝各供应商中模态标为「生图」的模型；加入后按列表顺序尝试，**第一个失败自动用下一个**；行内显示序号、名称、模型 ID、「首选／备选 N」标签、移出按钮；支持拖动排序与键盘 Alt+↑/↓；至少保留一个。
- **失败顺延规则**：单模型内先做参数降级链（`response_format` → `quality` → `size` → `n`，最多 4 次，逐次记入回退说明），仍失败才换下一个模型；鉴权失败、端点不支持等**不可修复错误也继续尝试下一个**；全部失败时汇总各模型错误（已脱敏）返回 AI。Anthropic 端点无 images 接口，标为不支持并跳过。
- **默认参数**：尺寸（1024×1024 / 2048×2048 / 4096×4096）、质量（low/medium/high/auto）、数量 n（1～4）、超时（5/10/15/30/60 分钟）四列一行。
- **输出目录**：相对应用数据目录，默认 `generated-images`；同名文件永不覆盖（自动加序号后缀）。
- **协议**：OpenAI 兼容 images（`/images/generations`；带参考图时 `/images/edits`，multipart `image[]`）；响应同时支持 `b64_json` 与 `url`（url 需下载转存），兼容中转站包一层的 `images`/`output`/`result` 信封。
- **端点与密钥**：复用所选模型所属供应商的端点与受管密钥，不单独填写。
- **AI tool 契约**：工具名 `generate_image`；参数 `prompt`（必填）、`model`、`size`、`quality`、`n`、`reference_images`、`path`；返回 `{ images: [{ filePath, mime }], model, prompt, paramsUsed, revisions, attempts: [{ model, error }] }`；AI 最终回复必须嵌入真实文件路径的图片，禁止虚构 URL。工具名与中文名映射并入 UI-CR060 的映射表（「工作台·生成图片」）。

### 4.4 CLI 管理（D1～D5）

- Grok 标志（2026-11-23 修正）：官方资源画布为 88×33，但矢量图形实际边界仅约 `x 0.36~33.70 / y 0.5~32.5`（约 33×32 方形），右侧 54 单位是空白。原设计的「横版字标按高度缩放＋定宽槽居中」会把这个偏左的可见图形连同右侧空白一起缩放，仍呈现偏左的视觉重心，用户据此反馈「歪了」。修正方式为把 SVG 的 `viewBox` 收敛到图形真实边界（`0.36 0.5 33.34 32`），与其他方形标志同样按 contain 填满槽位；不改图形路径、不裁切、不变形、不换非官方图。
- 移除「最低任务难度」「任务类型（CLI 级）」两个字段；CLI 是否被使用由主 agent 决定。
