## 1. 背景与现状事实

### 1.1 用户痛点

当前 AI 侧栏与项目工作台都必须先选定一个 CLI（Claude / Codex / Grok）才能开始对话：

- 未安装或未启用对应 CLI 时，界面直接阻止发送。
- 不同 CLI 支持的模型协议不同（Claude 需要 Anthropic 兼容，Codex／Grok 需要 OpenAI 兼容），同一个已配置模型不一定能被任意 CLI 使用。
- 用户需要理解「哪个 CLI 配哪个协议模型」才能发出一条消息。

### 1.3 当前断点（为什么必须新增本需求）

**断点一：对话被 CLI 绑定。**

`src-tauri/src/commands/chat.rs:550` 直接取 `session.cli_id`，缺失即报「会话未选择 CLI」；
`src-tauri/src/commands/chat.rs:596-608` 校验 `cli_sdk.installState='installed'`，未安装直接拒绝发送；
`src/modules/chat/ChatPanel.tsx:823` 前端同样拦截。

即使平台已经持有模型、密钥、Skill、知识、工具，**普通对话仍然必须经过一个外部 CLI 进程**。

**断点二：平台没有自己的模型调用客户端。**

`src-tauri/src/commands/model_probe.rs` 已有双协议 SSE 能力，但它是**探针**：
- `send_json:191-225`、`send_stream:227-268` 是探测用途；
- `build_body:358-409` 只支持 `(role, content)` 纯文本对，不支持 assistant 的 `tool_calls` 与 `tool` 角色消息；
- 没有多轮工具调用循环。

**断点三：执行引擎仍是 M0 模拟。**

`src-tauri/src/commands/execution.rs:1708-1900` 的 `dispatch_once` 注释明确写「M0 不 spawn 进程」，通过 `input.simulate` 走 `succeed/retry-once/retry-exhaust/fail/block` 分支。

`src/modules/projects/Workspace.tsx:283` 也如实标注「任务执行器与派发 API 尚未接入」。

**因此：本需求要补的是「平台自己的主代理执行通道」与「主代理到受管执行的派发接口」，而不是再建一套调度系统。**

## 2. 目标

1. **不选 CLI 也能对话**：平台会话可选择 `runner=platform`，由平台内置主代理直接使用已配置模型作答。
2. **平台继续掌权**：模型、端点、密钥、Skill、知识授权、工具启停仍由平台决定，主代理不接管配置权。
3. **工具边界结构化**：主代理只能调用平台批准的工具集，不具备任意 shell、文件写入、git 写、凭据读取能力。
4. **派发接口打通**：主代理可通过专用工具把工作交给受管执行，返回任务标识，而不是自己执行代码任务。
5. **完全兼容既有路径**：`runner=cli` 行为不变，可随时回退。

## 3. 不做事项

1. 不引入外部 Agent 框架作为运行时依赖（不新增 pi / DSH / OMP / ZCode 的 npm 或 cargo 依赖）。本需求走平台自有实现；外部项目只作机制参考，不进入正式依赖。
2. 不实现真实 worker 进程执行（M1 真实 spawn 属于 STORY-091 的后续增量，本次只交付派发接入与设计）。
3. 不做跨 CLI 原生线程迁移、不做多级子代理。
4. 不改 UI 视觉与交互；受影响界面另行补有效设计后实现。
5. 不做模型协议转换网关（不接 CCR / LiteLLM）；只使用平台已配置且协议匹配的端点。
6. 不做自学习路由；执行器与模型选择仍为显式配置＋主代理判断。

## 4. 业务流程

### 4.1 平台会话对话（STORY-089）

```text
用户发送
  → 读取会话 runner
  → runner=cli：走现有 chat_send（完全不变）
  → runner=platform：
      1. 解析会话绑定的供应商 / 模型 / 思考档位
      2. 校验供应商启用、端点启用、密钥可用、协议匹配
      3. 编译上下文（复用 build_prompt 的知识/Skill/引用边界）
      4. 组装消息数组：system + 历史 + 本轮
      5. 平台模型客户端发起流式请求
      6. 增量回传前端（复用 ChatEvent）
      7. 落库（复用 insert_assistant_messages）
```

### 4.2 工具循环（STORY-090）

```text
模型返回 tool_calls
  → 逐个校验工具名在平台允许集内
  → 校验工具未被停用（复用 tool_enabled）
  → 调用 run_tool（进程内）
  → 结果作为 tool 角色消息回填
  → 再次请求模型
  → 直到无 tool_calls 或达到轮次上限
```

**硬上限**：工具轮次 ≤ 8，单轮工具调用 ≤ 8，累计工具调用 ≤ 24。超限即终止并把已收集结果交回，不静默继续。

### 4.3 派发（STORY-091）

```text
主代理判断需要独立工作者
  → 调用 dispatch_work 工具
  → 平台校验：项目、Feature 归属、范围、预算、幂等键
  → 创建 execution_batch + execution_task + execution_plan
  → 返回 taskId / batchId
  → 主代理向用户说明已派发
  → 执行由受管调度器负责（本次不真实 spawn）
```

## 5. 规则与边界

### 5.1 主代理工具集（白名单，结构保证边界）

允许：

| 工具 | 用途 | 依据 |
| --- | --- | --- |
| `get_context` | 取当前项目上下文 | `ai_tools.rs:195-200`，实现 `631-653` |
| `list_projects` | 列出项目 | `ai_tools.rs:202-207` |
| `get_requirements` | 读需求树 | `ai_tools.rs:239-247`，实现 `684-689` |
| `read_requirement_doc` | 读需求正文（含 documentHash） | `ai_tools.rs:249-261`、实现 `690-718` |
| `write_requirement_doc` | 受限需求写入（需 expectedDocumentHash） | `ai_tools.rs:263-281`、实现 `884-996` |
| `list_kbs` / `knowledge_list` | 列知识库 | `ai_tools.rs:283-291`、`378-386` |
| `knowledge_search` / `knowledge_read` / `knowledge_read_many` | 授权内检索读取 | `ai_tools.rs:388-400`、`402-414`、`416-439`；实现 `1162-1243` |
| `fs_read` | 项目内只读文件 | `ai_tools.rs:365-376`，实现 `1126-1145` |
| `open_panel` | 请求打开右栏预览 | `ai_tools.rs:465-480`，实现 `1285-1302` |
| `list_servers` | 列服务器（不含密钥） | `ai_tools.rs:321-326`，实现 `1078-1100` |
| `dispatch_work` | **本需求新增**：派发工作包 | STORY-091 |

禁止（不注册即不可调用）：

- 任意 shell / pwsh 执行；
- 文件写入、删除、重命名；
- git 写操作；
- 凭据读取、供应商与密钥修改；
- `ssh_exec`（高风险执行，必须转用户在工作台显式审批，见 `ai_tools.rs:441-452` 定义与 `1245-1269` 实现）；
- 工具注册、插件安装、Skill 启停。

**这条边界不写在提示词里，而由工具注册表决定**：主代理运行时的工具清单是硬编码常量，模型无法通过参数扩展。

### 5.2 确定性前置（只做拦截，不做能力判断）

为避免明显无效请求进入模型循环：

| 条件 | 处理 |
| --- | --- |
| 内容为空或仅空白 | 前端已拦（`ChatPanel.tsx:809`），后端再拒 |
| 内容长度 > `MAX_PROMPT_TEXT`（`chat.rs:1132`） | 拒绝并提示减少引用 |
| 引用超限（>32 条） | 复用 `chat.rs:1186-1188` 的界限 |
| 会话未绑定可用供应商 | 明确报「请在设置中配置供应商」，不静默降级 |

**不做的判断**：不根据关键词猜「这是简单任务还是复杂任务」。这由主代理模型在工具调用中表达（是否调用 `dispatch_work`）。

### 5.3 失败分类与处理

| 失败 | 处理 | 不做什么 |
| --- | --- | --- |
| 供应商停用／端点缺失／密钥缺失 | 明确报错指向设置 | 不自动换供应商 |
| 协议不支持工具调用 | 明确报错并建议换模型 | 不假装支持、不退化到纯文本冒充 |
| 模型返回非法 tool_calls JSON | 记为工具错误回填，允许模型修正一次 | 不无限重试 |
| 工具执行报错 | 以 `isError` 回填，模型可换策略 | 不重试副作用类工具 |
| 流中断 | 复用 `chat.rs:1535-1544` 的限流/暂时不可用判定 | 不对 401/403 重试 |
| 超过工具轮次上限 | 终止并返回已收集内容，标注未完成 | 不静默成功 |

### 5.4 权限与授权

- `runner=platform` 会话不继承 CLI 权限模式（`plan/agent/auto/full` 针对 CLI 原生沙箱，见 `chat.rs:1015-1022`）。
- 平台会话的有效边界由三件事决定：工具白名单、工作层级授权、`dispatch_work` 的派发校验。
- 执行会话（`sessionRole='executor'`）仍受 Feature 绑定与源 hash 复检（`chat.rs:582-593`）。

## 6. 数据与兼容

- `session` 新增 `runner TEXT NOT NULL DEFAULT 'cli'`，取值 `cli` | `platform`；旧记录默认 `cli`，行为不变。
- 新增只读视图字段：`runner`、`platformModelRef`（可选，为空表示沿用 `providerId/modelId`）。
- 不新增第二套模型表；平台会话复用 `provider` / `provider_endpoint` / `provider_key` / `model`。
- 工具轮次与工具调用记录写入既有 `message` 表（`role='tool_use'` / `'tool_result'`），沿用 `insert_assistant_messages`（`chat.rs:1963-1993`）。

## 7. 验收标准

仅列需求级可观察结果，逐条可执行标准见各 Story。

- AC-069-01：未安装任何 CLI 时，新建 `runner=platform` 会话可完成一轮问答，回复落库并在刷新后保留。
- AC-069-02：平台会话的模型、端点、密钥来自平台设置；设置中停用供应商后发送被拒绝并说明原因。
- AC-069-03：平台会话可调用允许的 workbench 工具，工具步骤在侧栏可见，结果回填后模型继续作答。
- AC-069-04：平台会话无法调用禁止清单中的任何能力（shell、文件写、git 写、凭据读取、ssh_exec）。
- AC-069-05：工具被在设置中停用后，平台会话调用该工具被拒绝，而不是仍然执行。
- AC-069-06：主代理可调用 `dispatch_work` 生成受管批次与任务，返回标识；重复同一幂等键不产生第二个批次。
- AC-069-07：`runner=cli` 会话的所有既有行为（发送、续接、权限、绑定状态）保持不变。
- AC-069-08：协议不匹配或模型不支持工具调用时，明确报错，不静默换模型、不假装成功。
