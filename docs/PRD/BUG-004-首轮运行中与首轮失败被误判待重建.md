# BUG-004：CLI 首轮「进行中」与「首轮失败」仍被误判为待确认重建

- 类型：缺陷（会话绑定派生与首轮失败证据）
- 状态：**修复中**（2026-11-26 用户授权修复；结果见 [REPORT-BUG004](../Test/REPORT-BUG004-首轮运行态与失败重试验证.md)）
- 来源：用户 2026-11-26 截图反馈「派发子代理，还是有问题，没修复好吗？」：AI 会话发出「派发三个子代理…」后立刻出现「上下文待确认重建／原因：尚无原生续接引用（首轮未完成或历史来自旧版本）」，输入被锁。
- 关联层级：[EPIC-006 AI 会话与任务协作](../Plan/Epic/EPIC-006-AI会话与任务协作.md)、[FEAT-011 会话历史与后台任务](../Plan/Feature/FEAT-011-会话历史与后台任务.md)
- 关联 Story：[STORY-032 CR-037 普通侧栏原生续接](../Plan/Story/STORY-032-AI会话正式实现.md#cr-037-普通侧栏原生续接)
- 关联需求：[CR-037](CR-037-主代理协调与答疑.md)、[CR-068](CR-068-界面评审差异与会话可用性补正.md)（J11/J12）、[BUG-003](BUG-003-会话被误判为待重建上下文.md)

## 1. 现象

CLI 普通会话发出第一条消息后，只要本轮尚未结算（正在运行，或首轮直接失败），界面就会出现：
> 上下文待确认重建
> 原因：尚无原生续接引用（首轮未完成或历史来自旧版本）

输入被锁，必须点「确认重建…」才能继续；之后每次重发也会被后端拒绝（`BINDING_FRESH_REQUIRED`）。

本机库只读核对（2026-11-26 16:20，`data\db\workbench.db`，只读、不读正文）：

| 会话（前 14 位） | runner/cli | 消息 | 引用 | turn | 更新时间 |
| --- | --- | --- | --- | --- | --- |
| `sess-69bd12d43…` | cli/codex | user 1 / assistant 0 | 无 | 无 | 13:54:15 |
| `sess-6adb227d8…` | cli/codex | user 1 / assistant 0 | 无 | 无 | 13:54:52 |

同时该会话的 codex 沙箱日志显示 13:56–14:00 仍在执行工具，证明**本轮当时仍在运行**，而界面已把它报成待重建。

## 2. 触发判定的代码事实

- `src-tauri/src/commands/chat_binding.rs:573-621`：`derive_view` 只看 `session_role / runner / thread_ref / confirmed_turn_id / last_outcome / message_count`，**不接收运行态**；`message_count > 0` 且无引用、无 turn → `freshPending + REF_NOT_ESTABLISHED`。
- `src-tauri/src/commands/chat.rs:117-139`：`session_row` 调用 `derive_view` 时没有运行态来源；`chat_sessions / chat_session_get` 都走这里。
- `src-tauri/src/commands/chat.rs:49-64`：运行态由 `RUNNING` 表提供（`chat_status`），但未参与绑定派生。
- `src/modules/chat/ChatPanel.tsx:317-321`：`composerLocked` 直接信任 `binding`；`ChatPanel.tsx:1351` 同条件渲染横幅，均不排除运行中。
- `src-tauri/src/commands/chat.rs:717`：发送前 `resolve_binding(..., session.message_count > 0)` 把「只有一条 user 消息」当历史；首轮失败后再发仍被拒。
- `src-tauri/src/commands/chat.rs:1050-1053`：首轮 create 失败（`requested_resume=None`）直接返回，**不写 turn 行**，会话永久停在 `REF_NOT_ESTABLISHED`。

## 3. 影响

1. 正常的长任务（派发子代理、生图等）在运行中只要刷新/切换会话，就显示待重建并锁输入，用户误以为上下文已丢。
2. 首轮失败一次后，会话进入「必须确认重建」的死结；重发被拒，只能点重建并留下断点卡。
3. 运行中误点「确认重建」会改变绑定修订，使本轮结算变成 LATE、丢弃本轮引用。

## 4. 修复目标与验收标准

- **AC-BUG004-01**：给定 CLI 普通会话本轮仍在运行（user 消息已落库、无引用、turn 未结算），当读取会话元数据，则不派生 `freshPending/blocked`，不显示绑定横幅、不锁输入；本轮结束后恢复既有派生。
- **AC-BUG004-02**：给定首轮 create 失败且没有任何模型输出（无 assistant 消息、无引用），当失败轮结算，则写入 `outcome=archived、reasonCode=CREATE_FAILED` 的 turn 行。
- **AC-BUG004-03**：给定最新 turn 为 `CREATE_FAILED` 且无引用，当派生绑定状态与再次发送，则不要求确认重建，直接以 `create` 模式重发（不携带旧引用）。
- **AC-BUG004-04**：给定已有 assistant 输出或已结算为 `STOPPED/ADAPTER_REFUSED` 等、且无引用的会话，仍保持 `freshPending + REF_MISSING`，CR-068 J11「不静默 fresh」不回归。
- **AC-BUG004-05**：给定会话正在运行，当调用确认重建，则被拒绝且 `nativeThreadRef/nativeBindingRevision/nativeConfirmedTurnId` 不变。
- **AC-BUG004-06**：`runner=platform`、执行会话、`native/fresh/blocked` 既有行为与文案不变（BUG-003 不回归）。

## 5. 不包含

- 不改变 CLI 原生续接协议、兼容键、授权快照与 CAS 语义。
- 不恢复或改写历史消息；不做数据迁移；不改 `message` 表。
- 不把「运行中」伪装成已续接，也不为用户未确认的历史静默 fresh。
