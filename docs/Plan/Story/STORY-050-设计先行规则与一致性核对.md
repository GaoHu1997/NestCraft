# STORY-050：设计先行规则与一致性核对

- 类型：文档维护与差异审计，不是软件功能开发。
- 所属 Feature：[FEAT-001](../Feature/FEAT-001-工作台框架与可操作评审.md)。
- PRD：[PRD-001 CR-020](../../PRD/PRD-001-个人Agent界面需求.md#cr-020设计先行与视觉一致性约束)。
- 来源与确认依据：2026-11-19 用户指出实现未按 UI 稿、软件已有界面在设计中缺失，并明确要求“按照 UI 设计”“改动先改 UI 设计，再改软件，保证视觉统一”。此指令授权规则修订与核对，不冒充新设计稿已经验收。
- 负责人 / 优先级 / 状态 / 依赖：lead / 高 / 待验收（文档与资源检查已通过，非软件视觉验收）/ 既有规则、设计与正式代码可读。
- 目标：明确设计是视觉基准、设计覆盖与版本是开发门槛、真实对照是视觉交付门槛，避免后补设计与假报一致。
- 本次包含：修订研发规则与派发/验收要求；有限范围的设计/代码只读审计；登记基线继承、存量缺口、正式偏离与后续处理；同步导航。
- 本次不包含：补齐全部交互设计、正式软件视觉重构、新任务引擎、真实服务测试、生产发布。审计发现的实际 UI 问题仍未修复，不能计为本维护任务实现成果。

## 验收标准

- AC-STORY-050-01：给定界面新增或调整，研发规则明确先可视设计/覆盖/版本及适用确认，再修改软件；规则适用于主代理、子代理、小改动和重构，缺设计不派发 UI 编码。
- AC-STORY-050-02：给定软件已有但当前稿缺失、正式实现偏离旧有效基线、新设计仅待实现三类情况，审计分别登记来源、真实代码位置、关联任务、负责人/优先级/状态及下一步，不倒灌错误软件为设计或擅自取消存量能力。
- AC-STORY-050-03：给定界面交付，规则要求同条件设计/软件成对视觉证据，不能用构建、功能入口、共享令牌或设计稿自己的测试证明正式视觉一致；导航能找到基线与缺口。
- AC-STORY-050-04：给定本次纯文档改动，文档本地链接与需求层级、设计资源引用及 diff 检查有实际结果，软件和交互原型受保护，无未经验证的视觉通过结论。

## 简要方案与实现位置

按文档维护例外在本任务记录方案，无需新增无关 LLD 或 DB：先读既有规则/文档与 Git 状态，独立只读审计并由 lead 核对证据，局部修订 [AGENTS](../../../AGENTS.md)；建立 [UI-BASELINE-001](../../UI/文档/UI-BASELINE-001-设计与实现覆盖核对.md)，同步 PRD、父 Feature、需求汇总、文档导航和设计总览/说明。DB 不适用：不更改持久化数据、接口或权限。

不编辑正式源码、当前交互稿脚本/样式或冻结历史原型；不提交/推送。校验源码 SHA-256，与编辑前快照对比；审查本次文档 diff 保留既有改动。执行已有 `design-docs-check` 与 `cr017-docs-check`，它们只验证文档/资源，不是软件视觉对照。

## CR-021：明确编码授权边界增量

- 来源／范围：2026-11-19 用户明确“没有让你动代码”“没有明确让写代码的所有都是需求／设计调整”；只授权优化代理规则，不授权正式编码。
- AC-STORY-050-05：默认所有产品诉求、调整、优化、反馈只推进需求／设计；确认需求／设计与一般“继续／执行”不授权软件编码。进入开发或派发编码须有明确原话、范围、时间及有效设计；动手前记录工作层级与允许修改文件范围。
- 方案：在 AGENTS 的强制默认边界、执行原则、确认规则和 DoR 同步明确层级，不以“范围清楚”替代编码授权；可操作设计稿 HTML/CSS/JS 只限设计演示，无真实业务执行。需求文档及导航同步说明。
- 本轮正式源码仅只读审计和哈希保护，不修改／构建／运行正式软件；原 CR-020 规则审计与历史结果保留。CR-021 可视导航调整由独立 STORY-051 负责。
- 验证结果：[REPORT-014](../../Test/REPORT-014-管理与详情导航设计验证.md)，默认需求／设计、一般确认不授权编码、开发／派发需明确授权、文件范围四项检查通过；原 REPORT-012 保留为历史，不冒充本轮新增检查。
